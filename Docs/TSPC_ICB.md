# TSPC indexed-count ICB 工作区

每次 `MVKCommandEncoder` 编码独占借出的 ICB，按录制命令的最大 `maxDrawCount` 准备轮换工作区，包含 secondary command buffers 的需求。容量沿用 MoltenVK `mvkEnsurePowerOfTwo` 向上分档，避免需求微增触发大资源重建；下一档超出 uint32 时按请求容量分配。Immediate prefill 允许扩容，但被替换的资源仍由原 Metal command buffer 的完成回调持有，不能因替换工作区句柄而提前回收。

GPU 重用遵循 [Apple GPU ICB 示例的 Encode and optimize ICB commands / Execute the ICB](https://developer.apple.com/documentation/metal/encoding-indirect-command-buffers-on-the-gpu)：reset → compute conversion → render execution，保持 Vulkan 命令和 pass 顺序。ICB 使用 [tracked hazard tracking](https://developer.apple.com/documentation/metal/mtlhazardtrackingmode/tracked)，compute 声明写入，render 通过 [useResource(_:usage:stages:)](https://developer.apple.com/documentation/metal/mtlrendercommandencoder/useresource(_:usage:stages:)) 声明读取，使再次覆盖等待前次读取完成，不依赖 profiler 的 fence。轮换采用 [Apple 多缓冲 FIFO 模型](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/MTLBestPracticesGuide/TripleBuffering.html)；这里将生产者/消费者映射为同一次提交内的 GPU reset/compute 与 render，以 Metal hazard tracking 代替示例中 CPU 等待完成信号的同步。两份工作区允许相邻批次准备与消费重叠，再次使用同一份时仍受读后写依赖限制。

完成后的空闲缓存采用 [Apache Commons Pool `GenericObjectPool.borrowObject` / `returnObject`](https://github.com/apache/commons-pool/blob/rel/commons-pool-2.12.1/src/main/java/org/apache/commons/pool2/impl/GenericObjectPool.java) 的有界 LIFO 对象池规则：依次取出缓存，不适用的对象销毁后继续取；无可用对象时创建；达到 `maxIdle` 后直接销毁归还对象。此处的适用条件是 ICB 容量满足请求，空闲上限与一组轮换工作区数量一致；在途资源不受空闲上限限制，仅 GPU 完成后才进入归还流程。`vkTrimCommandPool` 和带 `RELEASE_RESOURCES` 的 command pool reset 清空闲置缓存，不提前回收在途资源。容量分档可能保留高于当前请求的容量；空闲上限过低也可能增加重建，需要由产品负载验证。
